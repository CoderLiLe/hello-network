# 第17讲 P2P协议

传统的 HTTP/FTP 下载是客户端-服务器模式，单一服务器带宽成为瓶颈。P2P（peer-to-peer）让每个下载者同时也是上传者，参与的人越多速度越快。

## FTP 协议（对比）

- **控制连接**：端口 21，传输命令（list/retr/store）
- **数据连接**：每传一个文件新建一个连接
- **主动模式**：服务器从 20 端口主动连接客户端
- **被动模式**：服务器开放随机端口，客户端去连接

## BitTorrent 协议

### 种子文件（.torrent）

包含两部分：
- **announce（Tracker URL）**：中心服务器地址
- **文件信息**：目录结构、文件名、每段大小、段哈希值

### 下载流程

1. 解析 .torrent，获取 Tracker 地址
2. 连接 Tracker，获取其他下载者（peer）的 IP
3. 连接其他 peer，交换数据块
4. 每下载一个块，计算哈希与种子的对比，验证正确性

依赖 Tracker 服务器：Tracker 挂了就找不到 peer。

## DHT（分布式哈希表）

去中心化方案，不需要 Tracker。每个节点既是下载者，也是 DHT 路由节点。

### Kademlia 协议

- 每个节点和文件都有 160bit 的 ID
- **哈希匹配规则**：文件哈希值匹配（或最接近）的节点负责知道该文件在哪些节点上
- **距离**：两个 ID 的 XOR 值，XOR 值越小越"近"（社交距离，非地理位置）

### 朋友圈分层（k-bucket）

按 ID 差异位数分层：只有最后 1 位不同 → k-bucket 1（1 个节点），倒数第 2 位开始不同 → k-bucket 2（2 个节点），以此类推。

每层只保留 K 个节点，按最近联系时间排序。最近联系过的放在最前面，满了就淘汰最旧的。

### 查找：折半查找

目标距离在 [2^i, 2^(i+1)) 范围，查 k-bucket i。找不到就找一个对目标更近的中间节点，让中间节点继续找，每次距离至少减半，最多 log2(N) 次找到。

### 四个指令

- **PING**：探测节点是否在线
- **STORE**：要求节点存储数据
- **FIND_NODE**：按 ID 查找节点
- **FIND_VALUE**：按 KEY 查找数据所在节点

每次执行指令都触发 k-bucket 更新（LRU 策略）。

## 99% 卡住的原因

下载的最后阶段，剩余的块在所有已知 peer 中都找不到，需要等待持有该块的 peer 上线。
