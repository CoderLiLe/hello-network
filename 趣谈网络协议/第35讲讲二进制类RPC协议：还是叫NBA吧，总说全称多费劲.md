# 第32讲 二进制 RPC（Dubbo）

## 数据中心内调用

微服务分层架构：

```
Controller 层（RESTful API 对外）
    ↓
组合服务层（复杂业务逻辑）
    ↓
基础服务层（原子接口，屏蔽缓存/数据库）
    ↓
缓存层（Redis/Memcached）+ 持久化层（数据库/ES）
```

数据中心内部调用量大，二进制比文本更省空间和带宽（数字 123 只需 1 字节 vs 文本需要 3-6 字节）。

## Dubbo 架构

```
客户端 Proxy(Stub) → 注册中心获取服务列表 → 路由+负载均衡 → Hessian2 序列化 → Netty 传输 → 服务端解码 → 线程池处理 → 返回
```

## Hessian2：自描述二进制

不需要协议文件，靠自身规则即可解析。每个类型起始数字唯一，看到数字就知道后续内容。

```
H x02 x00    # Hessian 2.0
C            # RPC call
 x03 add     # method "add"（3个字符）
 x92         # 两个参数（0x90+2，防止歧义）
 x92         # 参数1 = 2
 x93         # 参数2 = 3
```

对象传输：先传类型定义（类名、字段），再传对象引用类型定义，同类型对象用 0x60 简写。

## Netty 传输

非阻塞事件驱动：connected → received → sent → caught。异步读写分发到线程池处理。

## 二进制 vs RESTful 选型

二进制问题：DTO 变更需双方同步 JAR，微服务多了依赖复杂。

解决方案：
1. 严格项目管理：禁止循环依赖，接口兼容，先升级服务端再消费端
2. 改用 RESTful：不共享 JAR，各声明各的，JSON 灵活，性能通过横向扩展弥补
