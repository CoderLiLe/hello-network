# 第15讲 HTTPS协议

HTTP 明文传输，支付等敏感场景需加密。

## 加密基础

### 对称加密

加密和解密使用相同密钥。效率高，但密钥如何安全传输给对方是问题。

### 非对称加密

公钥加密、私钥解密（或反之）。公钥可公开传播，私钥保密。

**问题**：如何确认收到的公钥是真的？黑客可以冒充服务端给你假的公钥。

## 数字证书

由 CA（Certificate Authority，证书权威机构）颁发。证书包含：公钥、所有者信息、发证机构、有效期、签名。

**验证链**：用 CA 的公钥解密证书签名 → 验证哈希 → 确认证书未被篡改。CA 本身可能由更高级 CA 背书，最终追溯到根 CA（Root CA，全球信任的几个大机构）。

## HTTPS（TLS）握手流程

```
客户端                              服务端
  |-- Client Hello ---------------->|  (TLS版本、加密套件列表、随机数1)
  |<-- Server Hello ----------------|  (选定加密套件、随机数2)
  |<-- Certificate -----------------|  (服务器证书)
  |<-- Server Hello Done -----------|
  |                                  |
  |  (验证证书链)                     |
  |  生成 Pre-Master (随机数3)        |
  |  用服务器公钥加密 Pre-Master       |
  |-- Client Key Exchange --------->|  用私钥解密得到 Pre-Master
  |-- Change Cipher Spec ---------->|  用3个随机数生成对称密钥
  |-- Encrypted Handshake Message ->|  验证加密通信
  |<-- Change Cipher Spec ----------|
  |<-- Encrypted Handshake Message -|
  |                                  |
  |<==== 对称加密通信 ==============>|
```

整个过程：非对称加密用于传输对称密钥，之后大数据量通信全部使用对称加密。

## 防重放与防篡改

- **Timestamp + Nonce（随机数）**：保证请求唯一，同一请求不处理两次
- **签名**：对内容做不可逆签名，篡改后签名对不上

## 性能优化

- **TLS 1.3**：移除了 ServerKeyExchange，通过 key_share 一个 RTT 完成握手
- **QUIC**：基于 UDP，省略 TCP 三次握手，首次连接即可快速建立加密通道
