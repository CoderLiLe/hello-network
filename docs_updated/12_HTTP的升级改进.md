# HTTP 的升级改进

> 讲师: 李明杰 (小码哥教育)

## HTTP/1.1 的不足

- **同一时间一个连接只能对应一个请求**：大多数浏览器允许同时最多 6 个并发连接
- **只允许客户端主动发起请求**
- **头信息重复传输**：每次请求都需要携带头信息，通常 500~800 字节，使用 Cookie 时可能上千字节

## SPDY

SPDY（speedy 的缩写），是基于 TCP 的应用层协议，强制要求使用 SSL/TLS。

- 2009 年 11 月，Google 宣布 SPDY 为内部项目
- SPDY 不用于取代 HTTP，只修改了请求与响应的传输方式
- SPDY 是 HTTP/2 的前身
- 2015 年 9 月，Google 宣布移除对 SPDY 的支持，拥抱 HTTP/2

## HTTP/2

2015 年 5 月以 RFC 7540 正式发表。

> 根据 W3Techs 数据，截至 2019 年 6 月，全球有 36.5% 的网站支持了 HTTP/2。

### 主要特性

#### 1. 二进制格式
- HTTP/2 采用二进制格式传输数据，而非 HTTP/1.1 的文本格式
- 在协议的解析和优化扩展上带来更多优势

#### 2. 多路复用 (Multiplexing)
- 将 HTTP 消息分解为互不依赖的帧，交错发送
- 并行发送多个请求，互不影响
- 并行发送多个响应，互不干扰
- 使用一个连接并行发送多个请求和响应
- 不必再为绕过 HTTP/1.1 限制而做很多工作（如 CSS Sprites、合并文件、域名分片等）

#### 3. 优先级
- 每个数据流可以有权重（1~256）和依赖关系
- 客户端可以构建"优先级树"
- 服务器据此分配资源

#### 4. 头部压缩 (HPACK)
- 使用 HPACK 压缩请求头和响应头
- 极大减少头部开销
- 曾被 zlib 压缩取代，后被更安全的 HPACK 取代

#### 5. 服务器推送 (Server Push)
- 服务器可以对一个客户端请求发送多个响应
- 可主动推送额外资源，无需客户端额外请求

### 基本概念
| 术语 | 说明 |
|------|------|
| 数据流 (Stream) | 连接内的双向字节流，可承载多条消息 |
| 消息 (Message) | 与 HTTP 请求或响应对应，由一系列帧组成 |
| 帧 (Frame) | 通信的最小单位，每个帧包含帧头（标识所属数据流） |

## HTTP/3

Google 觉得 HTTP/2 仍然不够快，于是开发了 HTTP/3。

- 弃用 TCP，改为基于 UDP 的 **QUIC** 协议
- QUIC（Quick UDP Internet Connections），2013 年由 Google 实现
- 2018 年从 HTTP-over-QUIC 改为 HTTP/3

### 为什么不用新的传输层协议？
- 世界上的网络设备基本只认 TCP、UDP
- 修改传输层意味着操作系统内核也要修改
- 开发并应用新的传输层协议极其困难

### QUIC 的特性

#### 连接迁移
- TCP 基于 4 要素（源 IP、源端口、目标 IP、目标端口），网络切换时连接会变化
- QUIC 使用 Connection ID 标识连接，IP 或端口变化时连接依然维持

#### 解决的问题
- **队头阻塞 (Head-of-Line Blocking)**
- **握手延迟**：减少 RTT（往返时延）

### 存在的问题
- 据 Google 和 Facebook 称，QUIC 需要近 2 倍的 CPU 使用量
- Linux 内核的 UDP 部分没有得到像 TCP 那样的优化
- TCP 和 TLS 有硬件加速，而 UDP 很少有
